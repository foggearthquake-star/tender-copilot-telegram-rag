# PROJECT MEMORY: Tender Copilot

## 1. Что это за проект

`Tender Copilot` — Telegram-first AI-продукт для анализа тендеров на русском языке.

Главная задача продукта:
- помочь поставщику быстро понять, стоит ли участвовать в тендере;
- сопоставить тендер с профилем конкретной компании;
- показать объяснимое решение с доказательствами из документов;
- подготовить черновую структуру заявки;
- выдать результат в человекочитаемом PDF и в JSON для интеграций.

Это не "просто чат-бот", а workflow-инструмент для принятия решения и ускорения подготовки заявки.

## 2. Конечный результат, к которому ведет проект

Идеальный конечный результат v1:
- пользователь в Telegram настраивает профиль компании вручную или файлом;
- загружает один или несколько файлов тендера PDF/DOCX;
- система извлекает факты, строит поиск по фрагментам, принимает решение;
- пользователь получает один из статусов: `GO`, `REVIEW`, `NO_GO`;
- вместе со статусом получает причины, риски, доказательства, следующие шаги;
- получает структурированный черновик заявки;
- может скачать PDF-отчет и JSON-выгрузку.

Бизнес-результат:
- сократить время первичного разбора тендера;
- снизить число "непонятных" тендеров без обоснования;
- сделать решение прозрачным и пригодным для внутреннего согласования.

## 3. Ключевая продуктовая логика

Продукт отвечает на 4 главных вопроса:
- подходит ли тендер компании;
- какие есть риски и пробелы;
- какими фрагментами документов подтверждается вывод;
- как должен выглядеть черновик заявки.

Базовая логика решения:
- `GO` — критические проверки пройдены;
- `REVIEW` — данных или доказательств недостаточно, нужна ручная проверка;
- `NO_GO` — найден хотя бы один жесткий блокер.

Жесткие блокеры:
- отсутствуют обязательные лицензии/сертификаты;
- сумма тендера выше лимита компании;
- условия оплаты конфликтуют со стоп-факторами компании;
- регион тендера вне допустимой географии компании, если профиль подразумевает жесткое ограничение.

Обязательный принцип продукта:
- решение не должно быть black-box;
- у каждого важного вывода должны быть причины и текстовые evidence-фрагменты.

## 4. Целевой пользователь

Основной пользователь:
- малые и средние поставщики в России;
- команды, которые решают, подаваться ли на тендер;
- люди, которым нужен быстрый предварительный разбор без замены юриста или тендерного специалиста.

## 5. Ограничения v1

- язык продукта: только русский;
- источник документов: только ручная загрузка файлов;
- продукт не дает юридическое заключение;
- это MVP / portfolio-grade система, но уже с рабочей архитектурой и наблюдаемостью.

## 7. Главное по реализации сейчас

На текущий момент проект уже не пустой и не "черновик идеи". Реализованы основные рабочие части:

### Telegram UX
- есть бот на `aiogram`;
- поддержаны команды `/start`, `/help`, `/company_setup`, `/company_doc`, `/new_tender`, `/status`, `/runs`, `/decision`, `/bid_draft`, `/report`, `/export_json`, `/cancel`;
- есть reply-клавиатура и пошаговый сценарий;
- отдельно поддержана загрузка профиля компании файлом;
- отдельно поддержана загрузка пакета тендерных документов.

Ключевой файл:
- `execution/app/telegram/bot.py`

### Схемы данных
Есть Pydantic-модели:
- `CompanyProfile`
- `TenderInput`
- `TenderFacts`
- `DecisionReport`
- `BidDraftOutline`
- `StageLog`
- `TenderRun`

Ключевой файл:
- `execution/app/schemas/models.py`

### Pipeline
Пайплайн уже собран как последовательность стадий:
- получение загрузки;
- парсинг документов;
- нормализация фактов;
- индексация чанков;
- принятие решения;
- построение черновика заявки;
- генерация PDF;
- fallback в `REVIEW` при сбоях.

Ключевой файл:
- `execution/app/services/pipeline.py`

### Парсинг и OCR
- PDF читается через `pypdf`;
- DOCX читается через `python-docx`;
- при пустом PDF-тексте есть OCR fallback через `PyMuPDF + pytesseract`;
- текст чанкуется для retrieval.

Ключевой файл:
- `execution/app/services/parsers.py`

### Нормализация тендерных фактов
Из документов извлекаются:
- сумма;
- дедлайн;
- предмет тендера;
- сертификаты;
- регионы;
- условия оплаты;
- обязательства;
- deliverables;
- критерии оценки;
- специальные условия.

Ключевой файл:
- `execution/app/services/normalizer.py`

### Company profile extraction
Есть эвристический разбор профиля компании из загруженного документа:
- название;
- категории;
- регионы;
- лимит контракта;
- минимальная маржа;
- сертификаты;
- стоп-факторы;
- summary;
- focus areas;
- project examples;
- knowledge_text для дальнейшего контекста.

Ключевой файл:
- `execution/app/services/profile_from_doc.py`

### Decision Engine
Уже реализована интерпретируемая логика:
- сравнение требований тендера с профилем компании;
- проверка по лимиту суммы;
- проверка по сертификатам;
- проверка условий оплаты;
- проверка географии;
- оценка полноты данных;
- оценка evidence;
- возврат причин, рисков, next actions и score-полей.

Ключевой файл:
- `execution/app/services/decision_engine.py`

### Retrieval / Vector layer
Есть несколько режимов:
- локальный хеш-векторный store;
- адаптер под `Qdrant`;
- адаптер под `Pinecone`;
- при неудаче внешнего back-end система сваливается в local.

Ключевой файл:
- `execution/app/services/vector_service.py`

Важно:
- локальный retrieval сейчас lightweight и эвристический;
- для MVP это нормально;
- для качества реального прод-анализа это одна из потенциальных зон усиления.

### LLM integration
Есть отдельный сервис LLM:
- режим `heuristic` или `api`;
- клиент через OpenAI-compatible API;
- сейчас настроен под `polza.ai`;
- LLM используется не как единственный мозг, а как слой улучшения уже полученного решения и outline;
- есть retry/backoff через `tenacity`;
- если LLM недоступен, система продолжает работу без него.

Ключевой файл:
- `execution/app/services/llm_service.py`

### Генерация PDF
Есть сервис PDF-отчета:
- выводит статус;
- уверенность;
- причины;
- риски;
- доказательства;
- следующие действия;
- структуру заявки;
- поддерживает русские шрифты через системные Windows fonts.

Ключевой файл:
- `execution/app/reporting/pdf_report.py`

### Хранилище
Есть два слоя хранения:
- JSON repository для локального режима / MVP;
- Postgres repository при наличии `DATABASE_URL`;
- сессии пользователя — через Redis, но с fallback в память процесса.

Ключевые файлы:
- `execution/app/storage/repository.py`
- `execution/app/storage/postgres_repository.py`
- `execution/app/storage/session_store.py`
- `execution/app/storage/factory.py`

### Наблюдаемость и аудит
Проект уже учитывает operational side:
- статусы стадий;
- duration;
- warnings;
- errors;
- `run_id`;
- audit log в JSONL.

Это важно: проект думает не только о выводе, но и о сопровождении запуска.

## 9. Что является самым важным приоритетом проекта

Приоритет номер 1:
- надежно и объяснимо отвечать на вопрос "подаваться или нет".

Приоритет номер 2:
- давать не просто статус, а доказуемое основание решения.

Приоритет номер 3:
- ускорять подготовку черновика заявки на базе тендера и профиля компании.

Приоритет номер 4:
- оставаться устойчивым при неполных документах, сканах и сбоях внешних сервисов.

Приоритет номер 5:
- быть удобным именно в Telegram-first сценарии, а не как абстрактный backend.

Если выбирать, что защищать в проекте в первую очередь, то это:
- explainability;
- fallback behavior;
- практическая польза для поставщика;
- прозрачная логика `GO / REVIEW / NO_GO`.

## 11. Практические риски и слабые места проекта

Самые вероятные реальные зоны риска:

### 1. Качество extraction / normalize
Регулярки и ключевые слова в `normalizer.py` пока эвристические.
Это нормально для MVP, но на реальных тендерах может давать:
- неполное извлечение предмета;
- пропуск сложных требований;
- слабое покрытие формулировок.

### 2. Local retrieval не семантический в полном смысле
Локальный vector store строится на hash embedding.
Это быстро и автономно, но:
- не равно качественному embedding retrieval;
- подходит как fallback / MVP, но не предел качества.

### 3. Profile extraction тоже эвристический
Разбор профиля компании из документа работает по паттернам и ключам.
Для нетипичных документов может быть неполным.

### 4. Качество решения сильно зависит от качества evidence
Сама архитектура это понимает и уже переводит часть случаев в `REVIEW`.
Это правильно и важно сохранить.

### 5. Состояние среды не гарантировано
По факту текущий Python не содержит минимум одной важной зависимости (`reportlab`).
При последующей работе всегда помнить:
- сначала проверять окружение;
- потом делать выводы о регрессии кода.

## 12. Нефункциональные требования, которые нельзя ломать

Из `directions/non-functional.md` и реализации:
- нужен graceful fallback при недоступности внешних сервисов;
- нельзя исполнять содержимое загруженных файлов;
- нужно валидировать и обрабатывать файлы defensively;
- нужно сохранять статусы пайплайна;
- нужно логировать latency / errors / stage info;
- нужно иметь audit trail.

Это опорные требования. Их нельзя жертвовать ради "косметических" улучшений.

## 14. Как дальше правильно работать с этим проектом

При любой следующей задаче сначала держать в голове этот порядок:

1. Сверить задачу с `Directions`.
2. Понять, какой stage или слой системы меняется.
3. Не ломать explainability и fallback.
4. Проверять, как изменение влияет на:
- Telegram UX;
- decision status;
- evidence;
- bid draft;
- PDF/JSON export;
- observability;
- storage compatibility.
5. Отдельно помнить разницу между:
- проблемой в логике кода;
- проблемой в зависимостях/окружении;
- проблемой в качестве входных документов.

## 16. Короткое резюме для себя

Это рабочий MVP Telegram-бота для анализа тендеров с объяснимым решением, evidence-выводом, черновиком заявки и PDF/JSON-экспортом.

Самое важное в проекте:
- не просто "сгенерировать ответ", а принять прозрачное решение;
- опираться на профиль компании и документы тендера одновременно;
- при слабых данных честно уходить в `REVIEW`;
- сохранять устойчивость при сбоях LLM, vector backends и OCR;
- развивать качество extraction и retrieval, не разрушая текущий workflow.

Если в будущем нужно быстро вспомнить смысл проекта одной фразой:

`Tender Copilot = Telegram-инструмент для explainable tender go/no-go decisioning + bid draft acceleration для поставщиков.`
